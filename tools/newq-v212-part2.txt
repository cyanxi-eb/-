@@@Q|AE-1|AI 应用工程|5|4|ai-agents-from-zero|你会如何评估一个 RAG 或 Agent 系统的效果？
@@@A
评估先拆成**离线评测**和**在线评测**，再把问题拆到具体层级，而不是只盯一个总分。

**RAG 分两层看：**
- **检索层**：相关内容有没有被召回，引用片段对不对，badcase 卡在切块、召回、重排还是过滤。
- **生成层**：答案是否**忠实于证据**，引用是否正确，无依据时能不能**拒答**，最终对业务有没有帮助。

**Agent 分两类评：**
- **轨迹级**：有没有选对工具、参数对不对、有没有无效循环、是不是过早结束。
- **结果级**：最终任务有没有完成，输出质量和用户体验是否达标。

**在线评测看：** 用户满意度、转人工率、任务中断率、耗时、badcase 类型分布；Agent 还要看工具调用成功率、重试率、循环次数、人工兜底比例。

**自动评测：** 规则评测 + `LLM-as-a-judge` + 人工抽检结合。规则和 LLM 评测放大规模、做回归，人工抽检兜住高风险误判和评价漂移。

**关键：** 评测不能只告诉你“分数变低了”，而要能定位**到底哪一层出问题**——召回差、上下文组装差、生成幻觉、工具失败、终止条件不合理，修法完全不同。

**推荐闭环：** 先分层建指标 → 沉淀 badcase → 让 badcase 反过来驱动 Prompt、检索、工具和流程迭代。
@@@E
**追问：** RAGAS 这类框架适合做什么？——适合做检索与生成的自动化指标（忠实度、答案相关性、上下文召回等），用于规模化回归，但不能替代人工抽检。

**易错：** 只报一个“准确率 95%”。必须绑定具体任务（分类、抽取、客服问答），脱离场景的数字没有意义。
@@@END
@@@Q|AE-2|AI 应用工程|4|3|ai-agents-from-zero|什么是“幻觉”？应用层应该怎么缓解？
@@@A
**幻觉不只是“完全胡说八道”**，更常见的是“看起来很像真的，但细节、引用、时间点、权限范围或工具结果已经偏了”。所以不应把它当成单纯的模型问题，而是**一条链路上的系统问题**。

**四层缓解思路：**
- **知识层**：用 RAG、外部检索、引用和无依据拒答，让模型基于证据回答。
- **执行层**：把计算、查库、发消息、查订单这类事情交给 Tool，不让模型纯文本瞎编结果。
- **约束层**：结构化输出、schema 校验、关键字段规则校验、低温度策略，减少“格式对了但内容错了”。
- **治理层**：badcase 回灌、人工抽检、线上监控和降级，别把“模型大概率没问题”当上线条件。

**结论：** 幻觉很难被彻底消灭，工程目标不是“保证永不出错”，而是让它**可发现、可限制、可回滚、可复盘**。
@@@E
**追问：** RAG 为什么不能彻底消灭幻觉？——因为检索可能召回错、上下文可能被噪声淹没、模型仍可能“有引用但不忠实”。

**易错：** 把幻觉和 Prompt Injection 混为一谈。幻觉是**模型能力与链路**问题，注入是**外部恶意输入**问题，防护手段不同。
@@@END
@@@Q|AE-3|AI 应用工程|4|3|ai-agents-from-zero|多用户场景下，如何为 Agent 做安全沙箱隔离？
@@@A
单机 Demo 很多风险不会暴露，一旦进入多用户场景，安全隔离必须从“工具权限”上升到“**执行环境隔离**”。三层方案：

- **环境层**：用 Docker 或其它容器把每个任务/租户隔离，限制 CPU、内存、网络和文件系统访问范围。
- **系统层**：配合 seccomp、AppArmor、只读根目录、临时工作目录、非 root 用户运行，避免直接碰宿主机。
- **应用层**：对工具、文件访问、系统命令、外部连接做**白名单和审计**，不让模型拿到裸权限。

**执行代码/命令/读文件时：** 不靠 Prompt 或业务代码限制，而是把工作目录挂成最小权限空间，敏感目录不挂载，数据库密钥和主机凭据**不进容器**。

**职责区分：** MCP 或 Tool 负责“**能不能调**”，沙箱负责“**即使调了也跑不出边界**”，两者职责不同，最好一起上。
@@@E
**追问：** 已经有 MCP 权限控制了，为什么还要容器？——协议层的权限是“逻辑门”，容器是“物理墙”；逻辑门被绕过时，物理墙仍能兜底。

**易错：** 只做应用层参数校验就以为安全。代码执行类 Agent 必须靠容器 + 系统调用限制兜底。
@@@END
@@@Q|AE-4|AI 应用工程|4|3|ai-agents-from-zero|Agent 部署和运维要看哪些指标？
@@@A
至少五类指标：

- **效果指标**：任务完成率、用户满意度、引用正确率。
- **性能指标**：首 token 延迟、端到端延迟、P95/P99。
- **稳定性指标**：调用成功率、超时率、重试率、失败率。
- **成本指标**：token 消耗、工具调用成本、单任务平均成本。
- **治理指标**：人工接管率、审计日志完整性、异常任务复盘效率。

**多步骤 Agent 还要加：** 每一步的**成功率和卡点分布**。否则你只能知道“最终失败了”，却不知道失败发生在哪一层。

**与大模型应用上线指标的关系：** 上线前看的五维（效果/性能/成本/稳定性/治理性）在运维阶段要变成**可监控、可告警**的持续指标。
@@@E
**追问：** 怎么设计降级策略？——超时/失败时先降级到规则链路或缓存，再不行转人工；关键是降级本身也要有指标。

**易错：** 只监控最终成功率。链路一长，问题往往藏在中间某一步的重试和等待里。
@@@END
@@@Q|AE-5|AI 应用工程|4|3|ai-agents-from-zero|RAG 系统在实际部署中可能面临哪些挑战？
@@@A
RAG 真正上线后，难点通常不在“能不能检索”，而在“从索引到回答的完整链路能不能长期稳定运行”。挑战拆成六类：

- **数据侧**：文档解析质量、切块策略、表格与 PDF 处理、知识更新时效。源数据脏、切块不合理，后面全被拖垮。
- **检索侧**：Embedding 选型、召回质量、混合检索、重排效果、metadata 过滤。离线能答，一放量就暴露“召回不准、噪声多、漏关键片段”。
- **生成侧**：上下文组装、引用溯源、忠实度控制、拒答策略。检索了不等于不幻觉。
- **治理侧**：权限隔离、版本管理、引用可追溯、知识回滚。企业最怕的不是答错，而是**答了权限外内容**或说不清依据。
- **评测侧**：badcase 建设、离线与在线指标闭环。没有评测，你很难知道问题出在切块、召回、重排还是生成。
- **工程侧**：延迟、成本、缓存、可观测性、索引重建与运维。知识库一更新，是全量重建还是增量更新？

**结论：** 面试里要讲出“RAG 是一条从数据接入、索引构建、检索召回到生成回答的**完整链路**，任何一层出问题，最终答案都会出问题”。
@@@E
**追问：** 线上效果不好优先从哪层排查？——先看**输入分布是否变化**，再看检索，再看生成；多数问题落在“文档解析脏、chunk 太碎、召回噪声大、上下文组装差”。

**易错：** 只优化生成层（换更强模型），却不动检索和数据层，指标纹丝不动。
@@@END
@@@Q|AE-6|AI 应用工程|4|3|ai-agents-from-zero|如何确保 Agent 的行为安全、可控且符合人类意图？
@@@A
不能只寄希望于模型本身“够聪明”或“已经对齐过”。模型层的 SFT、RLHF/RLAIF 只提供**基础安全边界**，真正落地必须补**应用层治理**，分四层：

- **模型与提示层**：用 System Message 明确角色、边界、安全规则和拒答策略。
- **工具与权限层**：不给模型裸权限，所有 Tool 都要 schema 约束、鉴权、参数校验、最小权限暴露。
- **执行与流程层**：设置最大步数、超时、人工审批、转人工、失败兜底，避免无限循环和危险动作直接落地。
- **观测与审计层**：保留调用日志、trace、输入输出、关键决策点和人工复盘链路。

**再加一层生产视角：**
- **预算控制**：最大工具调用次数、时间预算、token 预算、费用预算。
- **熔断机制**：连续失败停止、异常率告警、重复无进展退出。

**总结：** 模型对齐解决“基础行为别太离谱”，应用治理解决“在你的业务系统里别出事”。稳的 Agent 一定是“模型能力 + 权限边界 + 流程控制 + 人机协同”一起做。
@@@E
**追问：** 哪些动作必须人工审批？——支付/转账、删改数据、对外发送、执行系统命令，这些不可逆或有外部副作用的动作。

**易错：** 认为“模型已经对齐了，不需要再加拦截”。对齐是概率性的，工程要求是确定性的。
@@@END
@@@Q|AE-7|AI 应用工程|4|3|ai-agents-from-zero|Agent 链路耗时很长时，如何定位性能瓶颈？
@@@A
一条链路跑几分钟，不能只说“模型太慢”，要把耗时**拆开**：

- **模型层**：单次推理时长、首 token 延迟、输出 token 长度。
- **检索层**：召回、重排、外部搜索、知识库请求耗时。
- **工具层**：API 延迟、浏览器动作、代码执行、等待外部系统返回。
- **编排层**：路由判断、Supervisor 判断、重复重试、串行等待。
- **结果层**：后处理、校验、存储、日志落盘。

**方法：** 给每一步打 **trace 和 span**，先看 wall time 花在哪，再决定是换模型、改链路、减少步骤，还是把串行改成并行。用 LangGraph 还要看**节点级耗时**、是否反复进入同一节点、有没有因为缺少明确完成信号而来回判断。

**关键结论：** 很多五分钟任务不是卡在单次模型调用，而是卡在**多步链路过长、工具等待、监督节点重复判断**，或中间没有明确成功信号导致反复检查——**性能问题很多时候是状态流转和执行闭环没设计好**。
@@@E
**追问：** 有没有遇到过偶发性慢？——重点看外部依赖抖动、重试风暴和缓存击穿，而不是模型本身。

**易错：** 一慢就换更强/更快的模型，结果瓶颈其实在工具等待和串行编排上。
@@@END
@@@Q|AE-8|AI 应用工程|4|3|ai-agents-from-zero|意图识别 / 任务路由应该怎么做？它和模型路由有什么区别？
@@@A
**先区分两件事：**
- **模型路由**：这次该用**大模型还是小模型**。
- **意图识别 / 任务路由**：这次请求到底该走 **FAQ、RAG、Tool、Agent、Workflow，还是直接转人工**。

**分层设计：**
1. **目标分类**：先定义清楚系统有哪些路由终点——闲聊、FAQ、知识问答、查状态、执行动作、复杂任务、人工兜底。
2. **路由机制**：**高确定性场景先用规则和关键词兜底**，模糊场景再用分类模型或 LLM 做语义判断。
3. **置信度治理**：**低置信度不强判**，允许澄清、降级或转人工，别让系统带着误判继续往下跑。

**工程上偏好多级路由：**
- 先做**业务意图路由**（FAQ / RAG / Tool / Agent）。
- 再做**子域路由**（如客服里再分订单、退款、工单、投诉）。
- 最后做**模型路由**（在具体链路里决定强模型还是轻模型）。

**评估指标：** 路由准确率、低置信度占比、误路由成本、澄清命中率，以及每条路由分支的最终任务完成率。
@@@E
**追问：** 什么时候规则路由就够了？——路由终点少、关键词特征明显、误判成本低时，规则更快更可控。

**易错：** 一上来就上“单层万能 LLM 路由器”。缺乏置信度治理时，一次误路由会把后面整条链路全部带偏。
@@@END
@@@Q|AE-9|AI 应用工程|3|3|ai-agents-from-zero|大模型应用的可观测性应该怎么做？
@@@A
至少做到三件事：**有日志、有指标、有 Trace**。也就是能看见请求怎么流过系统、每一步花了多久、失败在哪里、用了多少 token、最后输出了什么。

**具体落地：** 打通 `trace_id / request_id`，把入口请求、Prompt 版本、模型版本、索引版本、检索结果、工具调用、异常信息、耗时和 token 用量串起来。

**用了 LangChain / LangGraph 还要看：** 节点流转、状态更新、人工中断点、重试次数、最终退出原因。

**为什么 Agent 尤其重要：** 很多问题发生在**中间步骤**，而不是最终输出那一刻。真正有用的可观测性，不只是“最后报错了”，而是能告诉你：**它在哪个节点卡住、为什么重试、为什么结束、当时看到了什么状态**。
@@@E
**追问：** 平台日志能解决哪些排障问题？——能把“预测错误”还原成“可复现的输入+上下文+参数”，这是复盘的起点。

**易错：** 只记最终输入输出，不记中间状态和工具调用。Agent 出问题时，这些才是关键证据。
@@@END
@@@Q|AE-10|AI 应用工程|4|3|ai-agents-from-zero|控制大模型应用成本应该从哪些层面下手？模型路由怎么做？
@@@A
**成本控制四层：**
- **模型层**：高低配模型分层，大任务用强模型，小任务用轻模型。
- **上下文层**：压缩 Prompt，减少无效历史，控制返回长度。
- **检索层**：优化召回和重排，减少无意义进窗内容。
- **流程层**：减少不必要的 LLM 调用次数，能规则化就不要全靠模型。

**多数系统成本高不是因为模型贵，而是链路设计太浪费**：无差别全量检索、过长历史拼接、多次重复调用大模型、工具失败后盲目重试。

**模型路由三层：**
- **意图路由**：先判断这是 FAQ、RAG、工具调用、复杂 Agent，还是直接转人工。
- **复杂度路由**：简单分类、格式化抽取、轻量总结走小模型；多步规划、开放生成、复杂决策走大模型。
- **成本路由**：热点问题先查缓存，能规则化解决的不进大模型，高价值/高风险任务再给强模型预算。

**治理要点：** 看不同路由分支的完成率、延迟、每任务成本；看是否有问题被错误下沉到小模型；设计**小模型失败后升级到大模型**的回退机制。

**一句话：** 做得好的系统不是每次都用最贵的模型，而是能把“该省的地方省掉，该花的地方花对”。
@@@E
**追问：** 怎样避免为省成本把效果打穿？——路由必须配合评测，监控各分支完成率，并保留升级回退通道。

**易错：** 只做“压缩 Prompt”这种局部优化，忽略“无差别全量检索”和“重复调用”这些大头。
@@@END
@@@Q|PE-1|提示词工程|5|4|ai-agents-from-zero|System Message 和 User Message 应该怎么分工？
@@@A
**System 负责稳定约束，User 负责动态任务。**

- **System**：角色、目标、边界、安全规则、输出格式要求、工具使用规范。内容应尽量**稳定、少改**。
- **User**：用户当次任务、输入数据、补充上下文和个性化要求。

**这样拆分的好处：**
- 结构更清晰，便于**版本管理**。
- 更适合做**模板化、灰度和评测**。
- 效果波动时容易定位是“系统约束变了”还是“输入变了”。

**反面：** 把所有内容混在一段 prompt 里，后面排查效果波动会非常困难，也无法做差异化的版本管理和灰度。
@@@E
**面试追问：** 检索到的文档放哪？——当作**不可信材料**放在 User 或独立的消息角色里，**绝不与 System 规则同权**（这是 Prompt Injection 防护的基础）。

**易错：** 把安全规则写进 User 消息。用户消息是可被覆盖和引导的，安全约束必须锚定在 System。
@@@END
@@@Q|PE-2|提示词工程|5|4|ai-agents-from-zero|结构化输出有哪些常见做法？各自的优缺点是什么？
@@@A
从 Model I/O 主线看，结构化输出大致分“**后处理解析**”和“**前约束结构化输出**”两类：

- **纯 Prompt 约束**：直接要求模型按 JSON 返回。最简单、起步快；但模型多说一句话、少个逗号程序就容易崩，**稳定性最差**。
- **Output Parser**：如 `StrOutputParser`、`JsonOutputParser`、`PydanticOutputParser`。属于“模型已输出，我再转成程序可用数据”，适合 `prompt | model | parser` 经典链路。
- **Structured Output**：如 `with_structured_output(TypedDict / Pydantic / JSON Schema)`。属于“输出前就把 schema 定好”，让模型按结构生成并自动解析，**约束力更强**。
- **Function Calling / Tool Calling**：本质也是结构化输出，只是目标更偏“生成调用意图和参数”，适合工具调用与 Agent。

**细选：** `TypedDict` 适合字段固定的轻量场景；`Pydantic` 适合类型/范围/必填严格的业务场景；`JSON Schema` 适合跨语言、跨系统共享结构协议。

**生产建议顺序：** 能用原生结构化输出就用 → 需要强校验用 Pydantic 一类 schema → 即使已结构化输出，也要补**业务校验、缺省值处理和失败重试**。
@@@E
**一句话总结：** Prompt 只能“尽量要求它长成这样”，Parser 和 Structured Output 才是帮你把模型输出**真正接进程序系统**。

**易错：** 把“让模型输出 JSON”当成生产方案。它只是最弱的一档，缺少契约和校验。
@@@END
@@@Q|PE-3|提示词工程|5|4|ai-agents-from-zero|Prompt Injection 是什么？为什么 RAG / Agent 场景更要小心？怎么防？
@@@A
**本质：** 不可信输入试图**改写系统指令、诱导模型越权**，或让 Agent 执行原本不该执行的动作。

**不只来自用户直接输入**，也可能藏在网页、PDF、知识库文档、邮件甚至图片里——只要这些内容会被模型读到，就可能形成**间接注入**。所以在 **RAG、浏览器 Agent、代码解释器**这类会读外部内容的系统里，风险明显更高。

**五层防护：**
- **指令分层**：System 放稳定规则；User 和外部文档都视作**不可信输入**，不能与系统约束同权。
- **内容隔离**：检索片段、网页内容、用户上传文档只当“**待分析材料**”，不默认它们能发新指令。
- **工具权限**：写操作、危险操作走白名单、schema 校验和最小权限。
- **动作校验**：关键输出做规则校验，关键动作做确认、审批或 HITL。
- **观测与兜底**：记录注入样例、失败轨迹和异常调用，沉淀进评测集和拦截规则。

**最关键一句：** **RAG 不是安全层，知识库文档本身也可能带恶意指令。** 只要把“检索到的内容”直接当成“可信提示词”，系统就很危险。
@@@E
**追问：** 为什么微调和对齐不能从根上解决注入？——因为注入是**运行时输入**问题，不是模型权重问题；对齐降低概率，但无法保证确定性。

**易错：** 只防用户输入，忽略知识库/网页里的间接注入——而后者在 RAG 场景才是主战场。
@@@END
@@@Q|PE-4|提示词工程|4|3|ai-agents-from-zero|如何系统优化提示词并把准确率做上去？
@@@A
不要把它理解成“反复手改几句提示词”，而是当成一个**小型工程闭环**：任务拆解、样例驱动、评测回归、边界收敛。

- **先定义任务边界**：说清什么叫答对、什么叫答错，哪些情况必须拒答或澄清。
- **做输入分层**：稳定规则放 `System`，动态任务放 `User`，别把约束揉成一段长 prompt。
- **先修大问题再修措辞**：如果本质是缺知识、缺工具、缺流程，别用 Prompt 硬抬。
- **用样例和反例**：few-shot 示例、反例约束、输出格式示例，通常比抽象要求更稳定。
- **做结构化约束**：能用 schema、parser、structured output 的地方，别只写“请返回 JSON”。
- **建 badcase 集**：把线上错例沉淀成固定评测集，每次改 Prompt 都跑回归，而不是靠体感。
- **做版本和灰度**：Prompt、模型版本、温度、输出格式要求一起管理。

**务实提醒：** 所谓“准确率 > 95%”必须绑定具体任务（分类、抽取、格式生成、客服问答）；真正的目标是让某个具体任务在**固定评测集**上稳定达标。
@@@E
**追问：** 提示词怎么改都上不去怎么办？——判断缺的是知识（→RAG）、行为（→微调/结构化输出）、流程（→Workflow）、还是动态决策（→Agent）。

**易错：** 靠“感觉更准了”判断迭代效果。没有 badcase 集和回归，改动无法归因。
@@@END
@@@Q|PE-5|提示词工程|4|3|ai-agents-from-zero|Prompt 工程的边界是什么？为什么不能把所有问题都交给 Prompt？
@@@A
Prompt 更接近一种“**任务表达和约束手段**”，但它解决不了**知识缺失、复杂状态管理和强执行需求**。

- 需要稳定调用外部系统时 → 应走 **Tools / Function Calling**，而不是让模型在文本里“假装调用了接口”。
- 需要固定格式与语气 → **结构化输出 / 微调**更可靠。

**工程上更合理的分工：** Prompt 负责**表达规则**，RAG 负责**补知识**，Tools 负责**执行能力**，Graph / Workflow 负责**流程控制**。

**一句话：** Prompt 是入口，不是万能药；把不属于它的问题硬塞给它，只会得到一个又长又脆的提示词。

@@@Q|SA-1|SQLAlchemy|4|3|comate|什么是 ORM？为什么要用 SQLAlchemy 而不是直接写 SQL？
@@@A
**ORM（Object-Relational Mapping，对象关系映射）**：把数据库表映射成 Python 类、把行映射成对象，用操作对象的方式读写数据库，由框架负责生成和执行 SQL。

**为什么用 SQLAlchemy：**
- **减少样板代码**：CRUD 用对象操作，不用手拼 SQL 字符串。
- **防注入**：参数化查询由框架生成，天然规避 SQL 注入。
- **数据库无关**：同一套模型代码可切换 MySQL / PostgreSQL / SQLite，改的是连接串和驱动。
- **连接与事务管理**：内置连接池、Session、事务上下文，避免手写连接释放逻辑。
- **可维护**：表结构、关系（一对多/多对多）、约束都在模型层集中定义。

**SQLAlchemy 的两层结构：**
- **Core**：SQL 表达式层，贴近 SQL，用于精细控制。
- **ORM**：对象映射层，建立在 Core 之上，是应用开发的主用层。

**什么时候仍要直接写 SQL：** 复杂报表、批量聚合、性能敏感的语句——ORM 不该被教条化使用。
@@@E
**易错：** 认为 ORM 能替代 SQL 知识。ORM 生成什么 SQL、有没有 N+1、有没有走索引，仍然要看得懂执行计划。

**追问：** ORM 最常见的性能坑是什么？——**N+1 查询**：循环里逐个访问关联对象，产生大量查询；解法是用 `selectinload` / `joinedload` 预加载。
@@@END
@@@Q|SA-2|SQLAlchemy|5|4|sqla-doc|SQLAlchemy 的 Session 是什么？它的生命周期是怎样的？
@@@A
**Session 是本机与数据库之间的一次“对话”，也是一个“持有区（holding zone）”。**

**核心职责：**
- 提供 `SELECT` 等查询接口，返回并修改 ORM 映射对象。
- **Identity Map（身份映射）**：按主键维护对象的**唯一副本**，同一行不会有两个对象。
- **Unit of Work（工作单元）**：对象属性修改会被记录；查询或提交前，Session 自动 **flush** 待定变更到数据库。
- 对象可视为数据库行的**本地代理**，可 detach 后在别处使用，或重新关联新 Session。

**生命周期（基础模式）：**
1. 通常以**无状态**形式构造，此时不持有连接。
2. 一旦查询或持久化对象，从绑定的 Engine **checkout 一个连接并开启事务**（autobegin）。
3. 事务持续到 `commit()` 或 `rollback()`；随后连接**释放回连接池**，下次新事务用新连接。
4. 用 `Session.close()` 或 `with` 上下文管理器关闭，关闭时清除所有对象并释放连接资源。

**关键：** Session **不是缓存**，不缓存查询结果；且默认用弱引用存实例，**不适合当全局注册表**。
@@@E
**易错：** 把 Session 做成全局单例跨请求复用。Session 是**可变、有状态**对象，代表单个事务，**不能在线程或 asyncio 任务间共享**——准则是「Session per thread, AsyncSession per task」。

**追问：** 怎么拿到某对象所属的 Session？——`Session.object_session(obj)` 或 `inspect(obj).session`。
@@@END
@@@Q|SA-3|SQLAlchemy|4|3|sqla-doc|SQLAlchemy 2.0 的查询方式有哪些？select / execute / scalars 分别返回什么？
@@@A
SQLAlchemy 2.0 中“2.0 风格”查询已成为标准：**先用 `select()` 构造语句，再交给 Session 执行。**

**三种执行方式与返回：**
- **`session.execute(stmt)`**：返回 `Result` 对象（如 `Row` 对象列表），适合取**列级别的多字段**。
- **`session.scalars(stmt)`**：返回 `ScalarResult`，直接提取**第一列的 ORM 实体对象**（如 `User` 对象列表）。
- **`session.get(User, 5)`**：按主键获取**单个对象**，会先查 Identity Map，未命中再查库，**效率较高**。

**典型写法：**
- 取实体：`stmt = select(User).where(User.name == "ed")` → `session.scalars(stmt).all()`
- 取指定列：`stmt = select(User.name, User.fullname)` → `session.execute(stmt).all()` 得到 Row 列表
- 取单个：`session.scalars(stmt).first()` 或 `session.get(User, 5)`

**一句话：** `execute` 拿“行”，`scalars` 拿“对象”，`get` 按主键拿“单个对象”且优先命中身份映射。
@@@E
**易错：** 用 `scalars` 去取多列结果，会只拿到第一列，误以为“查不到数据”。

**追问：** 为什么 `get()` 更快？——因为先查 Identity Map（本 Session 已加载对象），命中则不产生 SQL；同时它按主键查询，本身也最省。
@@@END
@@@Q|SA-4|SQLAlchemy|4|3|sqla-doc|SQLAlchemy 中 flush、commit、rollback 各做什么？expire_on_commit 有什么坑？
@@@A
**flush（刷写）：** 把内存中的**待定变更**（pending changes）转成 SQL 发到数据库，但**不提交事务**。
- **Autoflush 默认开启**：在 `execute()`、查询、merge 前自动发生。
- **`commit()` 和 `begin_nested()` 总是先 flush**，不受 `autoflush=False` 影响。
- flush 失败会自动 ROLLBACK，但 Session 进入“非活动”状态，**必须显式 `rollback()` 才能继续用**。

**commit（提交）：** 无条件先 flush 所有待定变更，然后发 `COMMIT`；提交后连接释放回池。

**rollback（回滚）：** 回滚当前事务；pending 对象被 expunge，deleted 对象恢复为 persistent，其余对象 fully expired。

**expire_on_commit 的坑：** 默认 `True` —— `commit()` 后 Session 中**所有对象都被过期**，下次访问属性会**重新发 SQL 加载**。
- 在 Web 应用里，如果把对象交给视图/模板层访问，会**触发额外查询**（甚至 detached 后报错）。
- 常见做法是设置 `expire_on_commit=False`（尤其异步场景），提交后对象保留内存状态，避免意外查询。
@@@E
**易错：** 以为“改完属性就落库了”。不 commit 就不会提交；即使 flush 了，也可以 rollback 撤销。

**追问：** autobegin 是什么？——Session 构造时无事务，一旦 `add()`/`execute()`/改属性就**自动开启**事务；`session.in_transaction()` 可查状态，2.0 还支持 `autobegin=False` 强制显式开启。
@@@END
@@@Q|SA-5|SQLAlchemy|4|3|comate|如何在 FastAPI 中集成异步 SQLAlchemy？如何封装数据库访问层？
@@@A
**依赖与引擎：** 安装 `sqlalchemy[asyncio]` + 异步驱动（`asyncpg` / `aiomysql`）；用 `create_async_engine` 替代 `create_engine`，连接串带异步驱动（如 `postgresql+asyncpg://`）。

**Session 工厂：** 用 `async_sessionmaker(async_engine, expire_on_commit=False)` 生成 `AsyncSession` 类；**全应用只创建一次**，放全局配置。

**FastAPI 依赖注入（请求级 Session）：**
```python
async def get_db():
    async with async_session() as session:
        yield session

@app.get("/users/{uid}")
async def read_user(uid: int, db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(User).where(User.id == uid))
    return result.scalars().first()
```
**要点：** 每个请求一个 Session，用完由 `async with` 自动关闭，绝不跨请求共享。

**封装访问层的推荐分层：**
- **模型层（models）**：DeclarativeBase + `Mapped` / `mapped_column` 定义表。
- **仓储层（repository / CRUD）**：把“查用户 / 建订单”等操作封装成函数，**只接收 session 参数**，不自己建连接。
- **服务层（service）**：负责事务边界与业务编排，`async with session.begin()` 包住一个完整业务动作。
- **依赖层（deps）**：`get_db` 统一提供 Session，`Depends` 注入到路由。

**事务：** 用 `async with session.begin():` 自动 commit/rollback；需要手动控制时显式 `commit()` / `rollback()`。
@@@E
**追问：** 连接池怎么配？——`pool_size`（基础连接数）、`max_overflow`（最大溢出）、`pool_timeout`（取连接超时）、`pool_recycle`（回收时长，避免被数据库踢掉）；按并发量调，不要盲目调大。

**易错：** 在 `async def` 里用同步 Session / 同步驱动，会阻塞事件循环——异步链路必须全程异步。

**关联查询技巧：** 用 `selectinload()` 预加载关联对象，避免异步场景下懒加载报错和 N+1。
@@@END

@@@Q|SD-4|AI 场景设计|4|3|ai-agents-from-zero|Code Agent 怎么设计？它真正的难点在哪？
@@@A
Code Agent 的核心不是“会写几行代码”，而是能围绕代码任务完成 **读代码库 → 定计划 → 改文件 → 跑验证 → 根据结果继续修正** 的闭环。本质仍是 **模型 + 工具集 + 运行循环 + 当前状态**，只是工具和状态更偏代码场景。

**分层设计：**
- **任务理解层**：把需求转成明确目标（读代码 / 改 bug / 补测试 / 重构 / 答架构问题）。
- **代码库理解层**：用代码搜索、文件树、符号索引、依赖关系、提交历史建立**最小必要上下文**，不是把整个代码库塞进模型。
- **计划与执行层**：先列修改计划，再决定读/改哪些文件、跑哪些命令、需要哪些验证。
- **工具层**：搜索、读文件、编辑文件、运行测试、执行命令、看日志。
- **反馈闭环层**：根据 lint、测试、运行报错、diff 结果继续修正，而不是生成一次补丁就结束。
- **安全治理层**：限制执行权限、隔离危险命令、保留变更和执行日志。

**真正的难点在三处：** **上下文治理**（大代码库怎么只拿相关部分）、**验证闭环**（怎么判断修复真的生效）、**失败处理**（连续修不好时怎么停下来、交还给人）。
@@@E
**追问：** 千万行代码库最容易先卡在哪？——**跨文件定位**；靠符号索引 + 依赖图 + 检索收敛上下文，而不是扩大窗口。

**易错：** 把 Code Agent 当成“代码补全放大器”。补全解决“下一行写什么”，Code Agent 解决“整个任务怎么闭环”。
@@@END
@@@Q|SD-5|AI 场景设计|3|2|ai-agents-from-zero|如何设计一个 Deep Research 系统？它和普通 RAG 有什么不同？
@@@A
**普通 RAG** 更接近“先检索，再回答”；**Deep Research** 更接近“围绕一个复杂主题，先拆研究任务，再多轮检索、交叉验证、综合整理，最后输出结构化报告”。

**核心模块：**
- **查询规划器**：把复杂问题拆成子问题。
- **检索执行器**：面向搜索、数据库、知识库做**多源检索**。
- **信息融合层**：去重、冲突检测、证据对齐、可信度加权。
- **迭代控制器**：证据不足时**继续补检**，而不是一次性结束。
- **报告生成器**：输出摘要、正文、引用和时间戳。

**本质差异：** 从“**单轮问答**”升级为“**多轮研究流程**”。所以设计重点不只是召回率，还包括**规划质量、引用质量、可信度、过程可回放性**。

**实现倾向：** 更适合用 **Workflow 或 LangGraph** 这类显式编排来做，而不是完全交给一个黑盒对话 Agent——因为需要中断、补检和人工审核点。
@@@E
**追问：** 什么叫多源交叉验证？——同一结论在多个独立来源被证实才采纳；来源冲突时保留分歧并标注。

**易错：** 以为“把上下文塞得更长”就是 Deep Research。它考的是**研究过程和证据链**，不是窗口大小。
@@@END
@@@Q|SD-6|AI 场景设计|3|2|ai-agents-from-zero|如何设计 Python 代码解释器（安全执行）？
@@@A
本质是“**模型生成代码 + 安全执行 + 回传结果**”的闭环系统。

**核心分层：**
- **代码生成层**：模型把用户需求转成 Python 代码。
- **沙箱执行层**：隔离环境、**白名单模块**、超时限制、资源限制。
- **结果回传层**：收集 stdout、stderr、文件产物、图表和返回值。
- **状态管理层**：多轮执行时保留变量或工作目录。
- **安全治理层**：禁止危险系统调用、网络访问和越权读写。

**真正的难点不在“会不会运行 Python”，而在“如何既让它有执行能力，又不把宿主环境暴露出去”。**

**纵深防御：** 模块白名单只是第一层；还要配合容器隔离、只读挂载、非 root 运行、禁网、CPU/内存/时间配额，以及执行日志审计。
@@@E
**追问：** 如果 Agent 能执行系统命令，怎么防止它删库或读敏感文件？——容器隔离 + 目录最小权限挂载 + 敏感目录不挂载 + 凭据不进容器 + 命令白名单。

**易错：** 只靠“在 Prompt 里禁止危险操作”。安全必须由**执行环境**保证，而不是模型的自觉。
@@@END
@@@Q|SD-7|AI 场景设计|3|2|ai-agents-from-zero|如何设计类 Manus 的通用智能体？
@@@A
不宜先强调“通用”，而应先回到 Agent 的**最小骨架**：模型 + 工具集 + 运行循环 + 当前状态。所谓类 Manus，本质上是把这四层能力**扩展到更长任务链和更复杂任务空间**。

**模块组成：**
- **任务理解与规划模块**：把目标拆成可执行步骤。
- **工具调度模块**：统一接搜索、浏览器、代码执行、文件系统等工具。
- **状态与记忆模块**：维护任务上下文、待办和阶段成果。
- **执行与反思模块**：根据中间结果继续执行、修正或重试。
- **安全与治理模块**：权限控制、日志、失败恢复和人工接管。

**和普通 Agent 的区别：** 不在于“工具更多”，而在于它需要**长期推进任务、处理中间产物、管理复杂状态**，并在较长链路里保持稳定性。所以它更像一个**通用任务执行框架**，而不是单轮问答机器人的放大版。

**工程重心：** 状态管理 + 断点恢复 + 预算控制 + 可观测性，缺一不可。
@@@E
**追问：** 长任务怎么保证不跑偏？——阶段性检查点 + 明确终态 + 人工审批点 + 预算上限。

**易错：** 一上来就堆几十个工具。工具越多，选择越乱；分层暴露和工具检索才是关键。
@@@END
@@@Q|SD-8|AI 场景设计|3|2|ai-agents-from-zero|如何开发浏览器自动化 Agent？
@@@A
核心是把“**看页面、理解页面、操作页面、校验结果**”做成稳定闭环。

**分层设计：**
- **页面感知层**：拿到 DOM、截图、可交互元素信息。
- **决策层**：根据目标决定点击、输入、滚动、等待还是回退。
- **执行层**：调用浏览器自动化工具（如 Playwright）完成动作。
- **校验层**：确认动作是否生效，页面是否进入预期状态。
- **治理层**：超时、重试、幂等、防误操作和日志回放。

**最大难点**不在“会不会点按钮”，而在**网页不稳定、异步加载、状态漂移、误操作成本高**——所以必须把**验证和回滚**意识做进去。

**安全提示：** 浏览器 Agent 会读到网页内容，因此是 **Prompt Injection 的高危场景**；网页里的隐藏提示词要按不可信输入处理。
@@@E
**追问：** 怎么处理异步加载？——显式等待元素/网络空闲 + 状态轮询 + 失败重试，而不是固定 sleep。

**易错：** 用截图 + 坐标点击做一切操作，页面稍有位移就失效；应优先用语义选择器 + 可交互元素信息。
@@@END
