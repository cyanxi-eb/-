@@@Q|LLM-36|LangChain|4|3|LLM0903|如何用 Redis 持久化多用户对话历史？为什么要自定义一个“窗口裁剪”的 Memory 类？
@@@A
**基础用法：** LangChain 官方提供 `RedisChatMessageHistory`，直接把历史存到 Redis，支持 `session_id`、`url`、`key_prefix`、`ttl`。

**为什么要自定义：** 官方类**没有实现“只保留最近 N 轮”**的能力，历史会无限增长——既不省钱，也会把上下文撑爆。所以需要**继承 `RedisChatMessageHistory` 自己实现窗口裁剪**：

```python
class WindowedRedisChatMessageHistory(RedisChatMessageHistory):
    def __init__(self, window_size: int = 5, **kwargs):
        super().__init__(**kwargs)
        self.window_size = window_size
        self.max_msg_count = window_size * 2   # 一轮 = 一问一答

    @property
    def messages(self):
        all_messages = super().messages
        return all_messages[-self.max_msg_count:] if all_messages else []

    def add_message(self, message):
        super().add_message(message)
        r = self.redis_client
        r.ltrim(self.key, -self.max_msg_count, -1)   # 写入后裁剪，控制存储体积
        if self.ttl:
            r.expire(self.key, self.ttl)             # 续期，避免活跃会话被过期
```
**两个关键点：** 读时**切片**（只把最近 N 条拼进提示），写时 **LTRIM**（控制 Redis 里的存储体积）+ **EXPIRE 续期**。两者缺一不可：只切片不裁剪，Redis 会无限膨胀；只裁剪不切片，逻辑不清晰。
@@@E
**追问：** 为什么一轮要 `window_size * 2`？——因为一条用户消息 + 一条 AI 回复才算完整一轮。

**易错：** 只在读取时切片，忘了 `LTRIM`，Redis 里历史仍然无限增长，长期成本失控。
@@@END

@@@Q|LLM-39|LangChain|4|3|ai-agents-from-zero|为什么 Tool 的参数要用 Pydantic 定义 args_schema？它解决了什么问题？
@@@A
**只写函数参数还不够**：单纯靠类型注解和 docstring，模型对“参数含义、取值范围、是否必填”的理解是模糊的，容易出现参数缺失、类型错误、枚举乱填。

- 让工具描述从“散文”变成**契约**，显著降低参数级工具幻觉。
- 为审计、日志、幂等提供结构化输入，便于治理。
- 复杂参数（嵌套对象、列表、多选）有了统一表达方式。

**一句话：** schema 是模型和工具之间的**合同**；没有合同，就只能靠模型自觉，而线上不能靠自觉。
@@@E
**易错：** 认为“有类型注解就够了”。注解不进 schema，模型看到的可能只是一句模糊描述。

**追问：** 什么时候用 Pydantic，什么时候用更轻的 TypedDict？——需要强校验和字段约束用 **Pydantic**；字段固定、只求结构对齐可用 TypedDict。

@@@Q|LLM-40|LangChain|4|3|LLM0903|从用户提问到工具执行，LangChain 工具调用的完整链路是什么？

@@@Q|LLM-41|LangChain|4|3|LLM0903|LLMChain、SimpleSequentialChain、SequentialChain 有什么区别？如何用 LCEL 替代它们？
@@@A
**三种传统链的定位：**
- **LLMChain（基础链）**：最基础，**PromptTemplate + LLM（+ 输出解析）**，只能做**单步任务**——输入变量 → 填提示 → 调模型 → 出结果。
- **SimpleSequentialChain（线性顺序链）**：串联多个单步任务，但**每一步只能一进一出**，上一步输出直接作为下一步输入，像流水线。
- **SequentialChain（顺序链）**：更强、更灵活，**支持多输入多输出**，可为每一步自定义输入/输出变量名，并保留所有中间结果，适合复杂多步任务。

**用 LCEL 替代：**
- 基础链：`chain = prompt | llm | StrOutputParser()`
- 线性顺序链：直接串起来 `prompt1 | llm | StrOutputParser() | prompt2 | llm | StrOutputParser()`
- 多输入多输出链：用 `RunnablePassthrough.assign(...)` 把中间结果挂到字典上，逐步累加字段。

**为什么 LCEL 更好：** 所有组件统一实现 `Runnable`（`invoke/ainvoke`、`batch/abatch`、`stream/astream`），因此**天然可组合**，还免费获得流式、批处理和异步能力；传统链写法只保留了历史兼容价值。
@@@E
**一句话总结：** 基础链解决“一步”，线性链解决“一进一出的多步”，顺序链解决“多进多出的多步”；而 LCEL 用统一接口把三者都表达得更简洁、更灵活。

**易错：** 在新项目里继续用 `LLMChain`。它属于 classic 路线，官方主线已转向 LCEL / LangGraph。

3. **设计 Prompt**：明确**角色、工具使用规则、停止条件和输出边界**（System + Human 消息）。
4. **创建执行器**：classic 路线用 `create_tool_calling_agent` + `AgentExecutor`；1.x 路线用 `create_agent`（底层由 LangGraph 运行时驱动）。
5. **形成闭环**：模型决策 → 工具执行 → 结果回传 → 继续或结束；配套设置**最大迭代次数**与失败兜底。

**真正的加分点：** 不是背 API 名，而是能说清 **Agent 为什么会调用工具、什么时候停、失败了怎么兜底**。
@@@E
**追问：** 简单场景一定要上 Agent 吗？——不需要。单轮查天气/查新闻用 `Prompt + Function Calling` 就够；只有多步动态决策才值得引入 Agent。

**易错：** 只写 `create_agent(tools=...)` 就以为完事，忽略了 Prompt 里的停止条件、工具边界和治理设计。
@@@END
@@@Q|LLM-47|RAG|5|4|ai-agents-from-zero|请描述一个完整的 RAG 流水线，工程上最难的是什么？
@@@A
完整 RAG 分**索引阶段**和**检索阶段**：

- **索引阶段**：文档加载 → 清洗 → 切块 → 向量化 → 写入向量库，并补充**元数据**。
- **检索阶段**：接收问题 → 必要时 **query 改写** → 检索召回 → **重排过滤** → 上下文组装 → 交给模型生成答案 → 最后做**引用、脱敏和格式化输出**。

**工程上真正难的三件事：**
- 文档是否被**正确解析**。
- 切块是否**保留语义**。
- 检索结果是否**真的对当前问题有帮助**。

**结论：** 线上效果差，大多数时候卡在这三层，而不是卡在最后那一轮生成。所以面试里要强调“RAG 是一条**完整链路**”，而不是“检索 + 生成”两个词。
@@@E
**追问：** metadata 应该存哪些字段？——来源文件、页码、章节标题、文档版本、权限标签、时间戳等，用于引用追溯、权限过滤和增量更新。

**易错：** 把 RAG 效果问题全部归因于“模型不够强”，忽略解析、切块和召回。
@@@END
@@@Q|LLM-48|RAG|4|3|ai-agents-from-zero|什么是 Agentic RAG？它和“一次检索后直接生成”有什么区别？
@@@A
**传统 RAG** 更接近**固定流水线**：先检索一次，再把结果交给模型生成答案。
**Agentic RAG** 更接近**闭环过程**：模型或 Agent 会根据当前进展决定**要不要检索、检索什么、是否改写 query、是否继续补检**，甚至在发现证据不足时**主动回头重查**。

**最大区别不在“有没有检索”，而在检索是不是被当成一个动态决策过程来管理。**
- **传统 RAG**：流程稳定、成本可控、实现简单，适合单轮问答和大多数标准知识库场景。
- **Agentic RAG**：适合复杂问题、多跳证据、需要自检补检的场景；代价是**链路更长、成本更高、失控风险更大**。

**什么时候升级：** 一次检索经常拿不到足够证据；问题需要拆问、多轮求证或多源交叉验证；生成前需要判断“该查知识库、查网页，还是查业务系统”。

**必须配套：** 步数上限、预算限制、失败退出条件和可观测性——否则它很容易从“更聪明的检索”变成“更贵的随机游走”。
@@@E
**追问：** 什么时候坚持固定 RAG？——badcase 不集中在多跳和证据不足上时，固定 RAG 更划算。

**易错：** 一上手就做 Agentic RAG。多轮补检会把延迟和成本迅速拉高，收益却未必覆盖。
@@@END
@@@Q|LLM-49|RAG|4|3|ai-agents-from-zero|什么是 Lost in the Middle？它对 RAG 设计有什么启示？
@@@A
**Lost in the Middle** 指：上下文一长，模型往往更容易利用**开头和结尾**的信息，而把**中间**那部分关键证据“看见了但没用好”。

**对 RAG 的启示：** 不是把更多 chunk 塞进上下文就一定更好。如果中间噪声太多，真正关键的证据反而更容易被淹没。

**工程处理方式：**
- 先做 **rerank 和过滤**，再决定谁能进上下文。
- 尽量**减少低价值片段**，别把“可能相关”都塞进去。
- **重要证据优先放前面**，必要时做摘要或结论前置。
- 对复杂问题采用**分阶段检索**，而不是一次性把大段材料全塞进去。

**一句话：** **长上下文不等于高质量上下文**，RAG 的核心仍然是“把最有用的证据放到最容易被模型用到的位置”。
@@@E
**追问：** 这解释了为什么“加更多 chunk 反而更差”——噪声淹没有效证据是常见退化原因。

**易错：** 用“上下文窗口够大”作为把 top_k 调到很大的理由。
@@@END
@@@Q|LLM-50|大语言模型|3|2|ai-agents-from-zero|有了超长上下文模型，还需要 RAG 吗？
@@@A
**多数场景仍然需要，因为“能塞进去”和“应该塞进去”完全不是一回事。**

超长上下文让长文理解、少量文档内推理更方便，但企业里更常见的问题不是“窗口不够大”，而是：
- 知识总量太大，**没法每次都全塞**。
- 长上下文的**成本和延迟都更高**。
- **权限过滤、租户隔离、版本控制**不能只靠窗口硬塞解决。
- **审计和引用追溯**更适合通过检索链路来做。

**合理理解：** 长上下文**扩大了可处理范围，但没有消灭检索的价值**。它更适合少量长文档分析、上下文整合和复杂推理；RAG 更适合海量知识缩圈、权限过滤、证据引用和持续更新。

**一句话：** **长上下文不是 RAG 的替代品，更接近 RAG 的补充能力。**
@@@E
**追问：** 那么什么时候可以不用 RAG？——知识量小、文档少、更新少、无需权限隔离时，直接把文档塞进长上下文是更简单的方案。

**易错：** 认为“窗口一大，RAG 就过时了”。忽略成本、权限和追溯这三个真实约束。
@@@END
@@@Q|LLM-51|RAG|4|3|ai-agents-from-zero|复杂文档 RAG 或多模态 RAG 应该怎么做？
@@@A
**最大的坑：把 PDF、扫描件、表格、图片、网页全都当成“普通纯文本”处理。**

**更稳的做法先把解析层单独看待：**
- 先做**版面分析、OCR、表格提取、标题层级恢复**，而不是一开始就按字符切块。
- chunk 尽量**按结构块切**：标题、段落、表格、图注，而不是把一张表切成几段残缺文本。
- metadata 保留**页码、章节标题、文档版本、来源文件、坐标或结构位置信息**，方便引用和追溯。
- 查询时必要时走**多路召回**（文本召回 + 表格召回 + 图片说明召回），再统一重排和组装。

**结论：** 企业里复杂文档 RAG 往往比“模型选型”更影响上限——解析错了、表格碎了、图文对应关系丢了，后面再强的模型也补不回来。
@@@E
**追问：** 为什么设备手册、制度 PDF 特别难做 RAG？——版面复杂（多栏、表格、图注），OCR 噪声大，语义边界和视觉边界不一致。

**易错：** 只在检索层做优化，忽略解析层。解析质量是复杂文档 RAG 的天花板。
@@@END
@@@Q|LLM-52|RAG|5|4|ai-agents-from-zero|为什么企业项目里的 RAG 必须重视权限、版本和引用？
@@@A
因为企业知识不是“能查到就行”，而是“**要查对、查对权限范围、还能追溯来源**”。

- **权限**：向量检索必须做**租户隔离、角色过滤、文档级或段落级权限控制**，不能把安全寄希望于模型“自觉不回答”。
- **版本**：索引和源文档要**可追踪**，文档更新后要知道哪些向量需要**增量重建**；支持索引回滚。
- **引用**：如果答案不能**回溯到原文片段**，业务方很难建立信任，也不利于审计和复盘。

**结论：** 在企业里，RAG 不只是检索效果问题，更是**数据治理问题**。

**落地要点：** metadata 里带权限标签与版本号，检索时做**前置过滤**（而不是生成后再删减），引用要精确到片段并给出出处。
@@@E
**追问：** 如何避免用户问到权限外文档？——在**检索层**按用户身份过滤候选集，而不是让模型“看了别说”。后者一旦被诱导就会泄露。

**易错：** Demo 阶段不设计权限字段，上线时发现向量库里根本没有可过滤的元数据，只能重建。
@@@END
@@@Q|LLM-53|RAG|5|4|ai-agents-from-zero|RAG 效果不好时，你会怎么排查？
@@@A
按“**检索前、检索中、检索后**”三层展开：

- **检索前**：看 query 是否表达清楚，是否需要**改写、拆问、补充上下文**。
- **检索中**：看切块、Embedding、向量库索引参数、**top_k**、过滤条件、**重排**是否合理。
- **检索后**：看拼给模型的上下文是否过长、是否有噪声、是否出现**关键信息被淹没**、生成提示是否要求“无依据就拒答”。

**企业知识库还要额外查：** 文档质量、版本是否最新、**权限过滤是否误伤**。

**结论：** 很多所谓“模型不聪明”的问题，最后都能定位到**文档解析脏、chunk 太碎、召回噪声大或上下文组装差**。

**辅助判断：** 如何区分是召回问题还是生成问题？——把召回片段单独拿出来判断“正确答案在不在里面”：不在 → 召回问题；在但答错 → 生成问题。
@@@E
**追问：** top_k 是不是越大越好？——不是。过大引入噪声（结合 Lost in the Middle 反而更差），一般配合 rerank 做“宽召回 + 精排”。

**易错：** 一遇到效果差就换模型/调温度，忽略了分层排查。
@@@END
@@@Q|LLM-54|RAG|4|3|ai-agents-from-zero|什么是向量数据库？它和传统数据库有什么区别？为什么不能只用 MySQL？
@@@A
**定义：** 向量数据库是一种专门面向“**相似度检索**”的存储系统，用来保存向量、原始内容和元数据，并支持**近邻搜索（ANN）、过滤和召回**。

**和传统数据库的分工：**
- **传统数据库**：擅长**精确过滤、事务**和结构化查询。
- **向量数据库**：擅长按**语义相似度**做近邻检索。
- 两者不是替代关系，而是**分工关系**。

**为什么不能只用 MySQL：** 你当然可以把 Embedding 存进 MySQL，但数据量一上来，**近似向量检索、ANN 索引、混合检索和大规模召回**都会变得低效，工程复杂度明显上升。

**更常见的做法：** 结构化条件走传统数据库，语义召回走向量库，再通过 **metadata** 把两边结合起来。

**常见向量库：** FAISS（本地库）、Milvus、Qdrant、Weaviate、pgvector（PG 扩展）、Redis Stack 等。
@@@E
**追问：** pgvector 算不算“只用 MySQL/PG”？——它是把向量能力**内建**进关系库，适合数据量中等、想减少组件数量的场景；超大规模仍建议专用向量库。

**易错：** 认为向量库能取代关系库的精确过滤和事务能力。
@@@END
@@@Q|LLM-55|RAG|4|3|ai-agents-from-zero|Embedding 是什么？如何选择 Embedding 模型？评估它好坏看什么？
@@@A
**Embedding 的本质：** 把文本、图片这类原始内容变成一串**固定长度的向量**，让“语义关系”尽量映射成“空间关系”——也就是把“**意思接近**”变成“**距离接近**”。

**它最核心的价值：** 不只是“把文本编码成数字”，而是让系统第一次具备**按语义检索**的能力（语义搜索、相似匹配、去重、聚类、推荐、RAG 召回）。

**在 RAG 里：** Embedding 决定“问题和知识能不能在向量空间里正确相遇”。选错了，后面的向量库、重排、Prompt 再补，也只能在偏掉的召回上做优化。

**选型看三件事：**
- **语言和领域适配**：中文、英文、多语言、代码、法律、金融，适合的模型可能完全不同。
- **建库和查询一致性**：建库与查询尽量用**同一套 Embedding 模型**（底线）。
- **成本和延迟可接受**：不是维度越高、模型越大越好，要看知识库规模和查询量。

**评估分三层：** 检索层（相关片段是否更容易被召回、重排前后差距）、业务层（忠实度、引用准确性、任务完成率）、工程层（延迟、成本、接入复杂度）。

**结论：** 公开榜单只能做**初筛**；真要决定上线，要用**自己的知识样本和 badcase** 做对比。
@@@E
**追问：** 建库和查询用不同模型会怎样？——要么维度对不上，要么即使维度相同，相似度也**没有意义**。

**易错：** 只看 MTEB 等榜单选型，不做自有数据的小规模对比实验。
@@@END
@@@Q|LLM-56|RAG|3|2|ai-agents-from-zero|近似检索和精确检索怎么权衡？
@@@A
- **精确检索**：效果更可控，但在大规模数据下**成本高、延迟高**（本质是全量比对）。
- **近似检索（ANN）**：牺牲一部分精确性，换来更好的**吞吐和响应速度**，所以大部分线上系统优先用近似检索。

**工程上不是简单二选一，而是看业务要求：**
- **高风险检索、数据量不大、对结果一致性要求极高** → 可用精确或更保守的索引策略。
- **通用知识问答、商品搜索、海量文档召回** → 近似检索更现实，再配合 **rerank** 做补偿。

**核心权衡：** 用可接受的召回损失换取可用的响应速度，再用重排把最终质量补回来。

**常见 ANN 索引：** HNSW（召回高、内存大）、IVF（聚类倒排，需调 nprobe）、PQ（量化压缩，省内存损精度）等。
@@@E
**追问：** 怎么判断近似检索的损失能否接受？——用业务 badcase 和 recall@k 指标评估，而不是凭体感。

**易错：** 追求“100% 精确”导致线上延迟不可接受，最后整个链路被拖垮。
@@@END
@@@Q|LLM-57|RAG|3|2|ai-agents-from-zero|什么场景下知识图谱或 GraphRAG 比纯向量检索更有价值？
@@@A
当问题的核心不只是“**语义相似**”，而是“**实体关系、路径推理、多跳关联、结构化约束**”时，知识图谱或图数据库会更有价值。

**典型场景：** 设备故障排查、商品属性关联、组织关系、法规条文引用、依赖链分析、供应链依赖、人物事件网络——这些问题往往不是“哪段文字最像”，而是“**谁和谁怎么关联、要经过几跳才能到答案**”。只靠向量检索，容易召回到语义接近但**关系错误**的内容。

**GraphRAG 与传统向量 RAG 怎么选：**
- 先用**传统向量 RAG 打底**，解决大多数语义召回问题。
- 当 badcase 明显集中在**多跳关系、实体消歧、结构约束**时，再引入图谱增强。
- 真正落地常常不是二选一，而是“**向量召回 + 图谱召回 + 融合重排**”一起做。

**一句话：** 只有当问题核心在**关系结构**上时，图谱路线的收益才会大于复杂度。
@@@E
**追问：** 图谱更新和维护成本会不会太高？——会，所以它更适合结构稳定、关系价值高的领域（制度、依赖、组织），而不是频繁变动的短文知识。

**易错：** 默认上 GraphRAG。它的构建与维护成本远高于向量 RAG，需要 badcase 支撑才值得。
@@@END
@@@Q|LLM-58|RAG|4|3|ai-agents-from-zero|RAG 应该如何接入 Agent 执行链路？
@@@A
不能只理解成“先查一遍资料再回答”，更稳的做法是把检索能力做成 Agent **可按需调用的一环**。三种接法：

- **前置检索**：用户问题一进来先统一检索，再把证据交给 Agent 继续规划。
- **按需检索**：把 Retriever / Search 封成**工具**，Agent 在需要事实依据时主动调用。
- **后置校验**：先生成结果，再用检索做证据核对或引用补全。

**推荐组合：** “**按需检索为主，前置检索为辅**”。因为不是每一步都需要查知识库，有些步骤是规划、路由、参数确认或工具执行。把 RAG 做成**可调用能力**，能减少无效检索，也更适合多步任务。

**后置校验的定位：** 可以作为增强，但**不适合作为主链路**——会增加延迟，而且前面已经跑偏时，后面再校验修正成本更高。

**进阶：** 当出现“一次检索拿不到足够证据”的 badcase 时，再演进到 **Agentic RAG**（多轮检索 + 中途补检）。
@@@E
**追问：** 什么情况下从“一次检索”升级成“多轮检索”？——问题需要拆问、多跳求证、或多源交叉验证时。

**易错：** 把 RAG 固定成前置流水线，导致 Agent 在不需要知识库的步骤上浪费一次检索。
@@@END
@@@Q|LLM-59|大语言模型|5|4|ai-agents-from-zero|Token 和上下文窗口是什么？它们在工程上意味着什么？
@@@A
**Token** 是模型处理文本的基本**计量单位**，不等于“字数”或“单词数”。模型看到的是 tokenizer 切出来的一串 token。

**上下文窗口**是模型单次推理时**最多能看到多少 token** 的上限。工程上常说的 `8K / 32K / 128K`，本质就是“系统提示 + 历史对话 + 检索结果 + 用户问题加起来最多能塞多少 token”。

**工程意义非常直接：**
- 决定你能不能做**长文问答、多轮对话、大段 RAG 上下文拼接**。
- **token 越多，成本越高，延迟也更容易上升**。
- 超出窗口的内容会被**截断、压缩或根本进不了模型**，所以不是“塞得越多越好”。

**估算口径（经验值）：** 1 个中文字符约 `0.6` 个 token，1 个英文字符约 `0.3` 个 token，所以 `128K token` 粗略可近似成二十万级别的中文字符量级。但真实数字会因 tokenizer、语言、代码、标点和格式而波动。
@@@E
**追问：** 为什么不能死记“1 汉字 = 1 token”？——分词算法、语言混合、代码和特殊符号都影响切分，只能估口径。

**易错：** 把“窗口大”当成“可以无限塞历史”。成本、延迟和 Lost in the Middle 都会惩罚这种做法。
@@@END
@@@Q|LLM-60|大语言模型|5|4|ai-agents-from-zero|什么时候该用 Prompt、RAG、微调、Workflow、Agent？
@@@A
**最稳的判断方式：先判断问题到底是“缺知识、缺行为，还是缺流程能力”。**

- 模型本来就会，只是任务没描述清楚 → 用 **Prompt**。
- 缺的是私有知识、最新知识、外部知识 → 优先上 **RAG**。
- 缺的是稳定行为（固定格式、固定语气、固定分类习惯） → 考虑**微调**。
- 流程固定、节点明确、强调稳定和可审计 → 优先 **Workflow**。
- 路径不固定，需要边做边决定下一步、动态调用工具 → 考虑 **Agent**。

**压缩成一句话：**
- **Prompt** 解决任务表达问题。
- **RAG** 解决知识来源问题。
- **微调** 解决行为稳定问题。
- **Workflow** 解决固定流程问题。
- **Agent** 解决动态决策问题。

**真实项目口径：** 不会一开始就说“必须做 Agent”。大部分需求先用 `Prompt + RAG + Workflow` 就能覆盖；只有在任务开放度高、工具选择依赖中间结果、流程没法提前写死时，Agent 的价值才真正体现。

**补充：** RAG 和微调可以一起用——用 RAG 提供知识，用微调或强约束输出提升行为稳定性（如客服项目）。
@@@E
**追问：** 为什么多数企业项目不优先做续训？——成本高、见效慢、知识更新不灵活，而 RAG 能快速跟进知识变化。

**易错：** 把“效果不好”一律归为“该微调了”。先分清是知识问题还是行为问题。
@@@END

@@@Q|LLM-62|大语言模型|5|4|ai-agents-from-zero|上下文窗口、短期记忆、长期记忆分别是什么关系？
@@@A
- **上下文窗口**：模型**单次推理**能看到的内容上限。
- **短期记忆**：**会话级状态**，保证当前线程不断档。
- **长期记忆**：**跨会话**保留的用户或任务信息（偏好、画像、历史结论）。

**工程上不能把三者混为一谈：**
- 窗口是**昂贵资源**，不能无限塞历史。
- 短期记忆一般保留当前任务相关历史、摘要、线程状态。
- 长期记忆更适合存偏好、画像、历史结论和可复用事实，需要**按需检索**，不应每次全量放进 prompt。

**成熟系统的做法：** 窗口里只放**高信号上下文**，短期记忆保证**当前线程不断档**，长期记忆通过**数据库或向量库按需召回**。

**一句话：** 窗口是“这一次能看到多少”，短期记忆是“这次对话别忘”，长期记忆是“下次还记得你是谁的偏好”。
@@@E
**追问：** 记忆和 RAG 的区别是什么？——RAG 召回的是**外部知识**，记忆召回的是**交互过程中产生的信息**（偏好、结论、状态）。

**易错：** 把长期记忆当成“把所有历史都存起来每轮全塞”，既贵又稀释信号。
@@@END
@@@Q|LLM-63|大语言模型|4|3|ai-agents-from-zero|如何为 Agent 设计短期记忆和长期记忆系统？技术上通常怎么落地？
@@@A
**先分两层：**
- **短期记忆**：解决当前会话/线程不断档，核心是“读历史 → 拼进提示 → 调模型 → 写回历史”。
- **长期记忆**：解决跨会话保留偏好、画像、历史结论和可复用事实，核心是“**存结构化信息，按需召回**”，而不是每轮全量塞 prompt。

**技术落地：**
- **短期记忆**：把消息历史或线程状态持久化到**内存、Redis 或 checkpointer**，再通过 `MessagesPlaceholder` 或图状态在下一轮重新注入。
- **长期记忆**：放在**数据库、向量库**，或在关系很重要的场景放进**知识图谱**。

**LangChain / LangGraph 体系下的划分：**
- `RunnableWithMessageHistory + BaseChatMessageHistory` → 更适合理解为“**对话历史注入**”。
- LangGraph persistence / checkpointer → 更适合理解为“**线程级状态持久化**”。

**落地选择：**
- 聊天助手 / 轻量多轮问答 → 优先消息历史方案。
- 复杂 Agent / LangGraph → 优先 `thread_id + checkpointer`。
- 跨会话偏好、事实、画像 → 走长期存储，按需检索。

**一句话：** 短期记忆服务**当前任务连续性**，长期记忆服务**跨任务复用**，二者分开设计。
@@@E
**追问：** Redis 更适合做短期还是长期记忆？——**短期**。它擅长按会话 key 快速读写并带 TTL；长期记忆需要检索与结构化查询，更适合数据库/向量库。

**易错：** 用同一个存储同时承担两层职责，导致 TTL 策略和检索需求互相打架。
@@@END
@@@Q|LLM-64|大语言模型|4|3|ai-agents-from-zero|超长多轮对话如何兼顾“不断档”和“省 token”？
@@@A
**四种常见手段，可以组合使用：**
- **滑动窗口**：只保留最近 N 轮原文，简单直接，但容易**丢早期约束**。
- **周期性摘要**：每隔几轮把历史压成**结构化总结**，保留目标、已确认事实、待办和偏好。
- **检索式补充**：把旧对话写入**向量库或长期存储**，按当前问题召回相关片段，而不是把所有旧消息塞回窗口。
- **结构化记忆槽**：像城市、会员等级、偏好、关键状态这类固定信息直接落**键值或数据库**，不让模型每次“回忆”。

**工程判断口径：**
- 早期约束重要（如系统设定、订单信息）→ 至少要有**摘要或结构化槽**兜底，不能只靠滑动窗口。
- 历史量大且查询相关性强 → 走**检索式补充**。
- 状态字段明确 → 直接**结构化存储**，不占 token。

**结论：** 记忆系统不是“历史保存得越多越好”，而是要区分：什么该**原样保留**、什么该**摘要**、什么该**结构化**、什么该**按需检索**。
@@@E
**追问：** 怎么判断该用哪种？——看“这条信息未来会不会被用到”和“用到的触发方式”：确定性触发 → 结构化槽；语义触发 → 检索式；全局约束 → 摘要保留。

**易错：** 只做滑动窗口，结果用户早期说的关键约束被截断，模型反复问同一件事。
@@@END
@@@Q|DB-72|缓存与Redis|4|3|LLM0903|如何用 Redis 封装多用户的对话历史？
@@@A
**核心思路：** 对话历史按**会话维度**存 Redis，用 `key_prefix + session_id` 作为 key，天然支持多用户、多进程、可持久化。

**LangChain 官方封装：** `RedisChatMessageHistory` 直接提供 `Redis` 存取消息的能力，关键参数：
- **`session_id`**：会话标识，决定 key 的归属。
- **`url`**：Redis 连接串（如 `redis://host:port`）。
- **`key_prefix`**：key 前缀（如 `chat-order:`），便于按业务隔离和排查。
- **`ttl`**：过期时间（如 7 天），避免历史无限堆积。

**接入链的完整形态：**
```python
def get_session_history(session_id: str):
    return RedisChatMessageHistory(
        session_id=session_id,
        url='redis://172.16.51.212:16379',
        key_prefix='chat-order:',
        ttl=60 * 60 * 24 * 7,
    )
```
再配合 `RunnableWithMessageHistory(chain, get_session_history, ...)`，调用时传 `session_id` 即完成“读历史 → 拼提示 → 调模型 → 写回”。

**为什么用 Redis 而不是内存字典：** 多进程/多实例可共享、重启不丢、可设 TTL 自动清理、读写性能高。
@@@E
**追问：** key_prefix 有什么用？——按业务线/租户隔离历史，避免不同场景的会话 key 冲突，也便于单独排查和清理。

**易错：** 不设 `ttl`，历史永久堆积，Redis 内存持续增长。
@@@END
@@@Q|DB-73|缓存与Redis|4|3|LLM0903|如何实现“只保留最近 N 轮”的会话记忆？为什么要 LTRIM + 切片双管齐下？
@@@A
官方 `RedisChatMessageHistory` **没有“保留最近 N 轮”的能力**，需要自己继承并实现窗口裁剪。

**实现要点（两个动作缺一不可）：**
```python
class WindowedRedisChatMessageHistory(RedisChatMessageHistory):
    def __init__(self, window_size: int = 5, **kwargs):
        super().__init__(**kwargs)
        self.max_msg_count = window_size * 2      # 一轮 = 问 + 答

    @property
    def messages(self):                            # ① 读时切片：只把最近 N 条拼进提示
        all_messages = super().messages
        return all_messages[-self.max_msg_count:] if all_messages else []

    def add_message(self, message):                # ② 写时裁剪：控制 Redis 存储体积
        super().add_message(message)
        r = self.redis_client
        r.ltrim(self.key, -self.max_msg_count, -1) # 只保留尾部 N 条
        if self.ttl:
            r.expire(self.key, self.ttl)           # 续期，活跃会话不被过期
```

**为什么两个都要：**
- **只切片**：模型上下文控制住了，但 **Redis 里历史仍在无限增长**，存储成本失控。
- **只 LTRIM**：存储控制住了，但读取逻辑不透明，且无法灵活调整窗口大小。

**一句话：** 读取时切片管“给模型看多少”，写入时 LTRIM 管“Redis 存多少”，`EXPIRE` 管“什么时候清”。
@@@E
**追问：** 为什么一轮要乘 2？——一次用户消息加一次模型回复才算完整一轮，只算条数会把对话切成半截。

**易错：** 忘了 `expire` 续期，导致活跃会话在 ttl 到点后被清空（因为每次写入不会自动续期）。
@@@END
@@@Q|DB-74|缓存与Redis|3|2|LLM0903|用 Redis 存对话历史时，key_prefix / ttl / session_id 应该怎么设计？
@@@A
**三个参数各管一件事：**

- **`session_id`**：会话的**唯一标识**，决定历史归属。每次对话调用都要传，通常由业务生成（如 `session_00005`、订单号、访客 ID + 时间戳）。
- **`key_prefix`**：Redis key 的**命名空间**，按业务线/租户隔离。如 `chat-order:`（订单客服）、`chat-hr:`（HR 助手），避免不同场景 key 冲突，也便于批量排查和清理。
- **`ttl`**：**过期时间**，控制历史保留周期。如 `60*60*24*7`（7 天）。不设会无限堆积。

**设计建议：**
- key 建议带上业务与用户维度：`{key_prefix}{user_id}:{session_id}`，既隔离又便于按用户清理。
- TTL 按业务定：短期客服可几小时，长期陪伴类可数十天；活跃会话需**续期**。
- 敏感场景做**加密或脱敏**，避免 Redis 里出现明文隐私数据。
- 高并发下用**独立 Redis 实例或 db 编号**与会话缓存隔离，避免挤占业务缓存。

**一句话：** `session_id` 定“这是谁的历史”，`key_prefix` 定“放在哪个抽屉”，`ttl` 定“多久后扔掉”。
@@@E
**追问：** 为什么程序里传 session_id 而不是 user_id？——一个用户可能开多个会话，用 user_id 会让不同会话互相串台。

**易错：** key 里不带用户维度，多租户场景下可能出现跨用户读取或清理误伤。
@@@END
@@@Q|DB-75|缓存与Redis|4|3|LLM0903|如果使用 Redis 或 SQL 来封装数据访问代码，应该怎么设计？
@@@A
**核心原则：把“连接管理、会话管理、业务逻辑”三层分开，业务代码不直接碰连接。**

**Redis 封装（三步模板）：**
- **连接层**：用**连接池**创建客户端（`redis.ConnectionPool` + `Redis(pool)`），全局只建一次。
- **仓储层**：把 `get / set / del / expire / lpush / ltrim` 等操作封成函数，业务只调函数，不写原始命令。
- **依赖层**：在 FastAPI 里用 `Depends` 注入客户端，请求级复用、统一关闭。

**SQL 封装（SQLAlchemy 分层）：**
- **引擎层**：`create_engine` / `create_async_engine` 建连接池，全局唯一，配置 `pool_size`、`max_overflow`、`pool_recycle`。
- **会话层**：`sessionmaker` / `async_sessionmaker` 生成 Session 工厂；**每请求一个 Session**，用 `with` / `async with` 保证释放。
- **仓储层（repository / CRUD）**：把“查用户 / 建订单”等操作封成函数，**只接收 session 参数**，不自己建连接。
- **服务层（service）**：负责**事务边界**与业务编排，`with session.begin():` 包住一个完整业务动作。
- **依赖层**：`get_db()` 提供 Session，`Depends` 注入路由。

**共同要点：**
- **连接必须池化**，绝不能每次请求新建连接。
- **资源必须自动释放**（上下文管理器），异常也要保证归还。
- **业务层只依赖抽象接口**，便于替换实现（Redis → 本地缓存，MySQL → PostgreSQL）和单元测试 mock。
@@@E
**追问：** 为什么仓储层不自己建连接/事务？——职责单一：它只负责“怎么读写”，事务边界由服务层决定，这样才能跨多个仓储操作构成一个原子业务动作。

**易错：** 在业务函数里到处 `redis.Redis()` 或 `create_engine()`，导致连接泄漏、连接数打满。
@@@END
@@@Q|SK-9|软技能|4|3|ai-agents-from-zero|面试官让你介绍一个做过的 RAG / Agent 项目，你应该怎么讲？

**最稳的讲述顺序：`业务目标 → 方案设计 → 你负责的部分 → 难点 → 指标结果`。**

**易错：** 一开口就是技术栈清单；或者把团队成果全部说成个人成果，一追问就露馅。

@@@Q|SK-10|软技能|3|2|ai-agents-from-zero|面试官问“你们为什么不用某个更热门的框架或模型”，怎么回答更稳？
@@@A
回答重点不是证明“当前选择永远最对”，而是说明“**当前选择和业务约束是匹配的**”。按四层展开：

- **业务复杂度**：当前问题到底需要单 Agent、Workflow，还是已经复杂到必须上 LangGraph / 多智能体。
- **工程约束**：团队熟悉度、交付周期、可观测性、可维护性、迁移成本。
- **部署条件**：直接用在线模型，还是接 OpenAI 兼容 API、本地模型、Ollama、Xinference 自建推理层。
- **成本与性能**：延迟、吞吐、token 成本、模型版本稳定性、第三方版本漂移风险。

**示例表述：** 没选更重的多智能体框架，是因为当前任务用单 Agent 或 Workflow 已经够了；没选更大的模型，是因为延迟和成本不划算；没选某个托管平台，是因为更看重统一 API、模型可控和私有化部署能力。

**再补两点更加分：** 你知道替代方案（不是没调研过）；你给当前方案留了**迁移路径**（不会把系统锁死）。
@@@E
**追问：** 如果未来需求变复杂，迁移路径是什么？——先想清楚“哪一层会先变”，比如从 Workflow 升级到 LangGraph 时，把节点逻辑与编排解耦。

**易错：** 贬低其它框架或一味说“我们用的就是最好的”，显得缺乏选型判断。
@@@END
@@@Q|SK-11|软技能|3|2|ai-agents-from-zero|你常用哪些 AI 开发工具？Cursor / Claude Code / Copilot 怎么选？
@@@A
**按场景分层，而不是罗列名字：**
- **通用对话与研究类**：`ChatGPT`、`Claude`、`Perplexity` —— 快速验证想法、梳理方案、写初稿、资料总结。
- **AI 编码协作类**：`Cursor`、`Claude Code`、`GitHub Copilot`、`Comate` —— 读代码、改代码、补测试、解释代码库。
- **低代码 / 工作流平台类**：`Coze`、`Dify` —— 业务快速验证、工作流编排、知识库接入、多人协作。
- **RAG / 知识库平台类**：`RAGFlow` —— 文档导入、解析、切块、检索与引用链路验证。

**编码工具的差异（协作位置不同）：**
- **Cursor**：偏 **IDE 内协作**，边看边补全、局部改写、基于当前文件/工作区编辑。
- **Claude Code**：偏**终端里的代码库级 Agent**，跨文件理解、执行命令、改一组文件、完成更完整任务。
- **Copilot**：偏**轻量级补全**，优势在低打断、嵌入现有编辑器工作流。

**判断标准（比名字更稳定）：** 对**代码库上下文的理解深度**、**执行边界与可控性**、是否契合团队工作流。

**真实项目里的组合：** 前期用通用对话工具梳理方案 → 用低代码平台做 POC → 用 AI 编码工具接手核心链路 → 最后补齐评测、部署和可观测性。
@@@E
**易错：** 简单比较“谁更强”。工具能力持续变化，回答应回到**任务类型**和**选型标准**上。

**加分点：** 说清楚“什么任务用什么工具”，并提到执行边界、可控性与团队工作流。
@@@END
